# CMWP/1.1 — Canonical Memory Write Protocol Design

- **Design workstream:** DCP-02C-7
- **Status:** User-approved design; implementation not authorized
- **Date:** 2026-11-24
- **Target repository:** `mohammadrezayaghoobi123-dev/Master-Brain-MCP-Hub`
- **Design branch:** `docs/dcp-02c-7-cmwp-1.1-design`
- **Scope:** Cross-boundary contract for Hub clients and the Backend persistence service

## 1. Purpose and decision

CMWP/1.1 defines a safe protocol for idempotent canonical memory writes, explicit closure of ambiguous operations, Backend-authoritative fencing, and loss-aware legacy compatibility.

The design combines:
1. Application-level orchestration and compatibility adapters.
2. Database-enforced uniqueness, transaction atomicity, and fencing.
3. Formal state-machine analysis and deterministic empirical fault testing.

The protocol makes no exactly-once claim for effects outside the PostgreSQL transaction. It distinguishes safety from liveness and does not interpret an unknown outcome as success or failure.

## 2. Non-goals and authorization boundary

This document is a design artifact only. It does not authorize implementation, schema migration, endpoint deployment, database modification, production changes, merge, or release.

The following are explicitly out of scope:
- Implementing API handlers, SQL migrations, triggers, stored procedures, or client changes.

## 4. Protocol identity and namespace

An idempotency key identifies one logical operation, not merely a payload.

The uniqueness namespace is the tuple:

```text
(tenant_id,
 subject_id,
 client_namespace_id,
 operation_name,
 contract_major_version,
 idempotency_key)
```

Definitions:
- `tenant_id`: authenticated tenant boundary.
- `subject_id`: authenticated principal on whose authority the operation is executed.
- `client_namespace_id`: stable registered client/application namespace.
- `operation_name`: canonical operation identifier, e.g. `memory.create`.
- `contract_major_version`: major protocol contract version.
- `idempotency_key`: opaque, high-entropy operation identifier generated once and reused for retries.

The operation namespace is distinct from the actor performing an administrative action. A Close request may be initiated by an operator different from the original subject; it targets the original operation namespace while recording and authorizing the acting principal separately.

The payload fingerprint is a separate value. A content hash must not be used as the sole operation identifier.

## 5. Canonical request fingerprint

The Backend computes the fingerprint after authentication, authorization, and canonical validation. A client-supplied fingerprint is advisory at most and is never authoritative.

Proposed construction:

```text
SHA-256(UTF-8(JCS(operation || contract_version || canonical_payload)))
```

Canonicalization requirements:
- Use a versioned canonicalization algorithm; persist `canonicalization_version` with the ledger entry.
- Preserve string contents exactly; do not normalize whitespace or Unicode implicitly.
- Preserve array order unless the operation schema explicitly defines set semantics.
- Distinguish absent fields from explicit `null` where the contract distinguishes them.
- Reject duplicate JSON object keys and values outside the contract's numeric range.
- Unknown fields must be explicitly preserved or rejected; they must not be silently discarded.
- Retain each supported canonicalizer for at least the full idempotency-key validity horizon.
- A retry must be interpreted using the canonicalization version bound to the original key.

RFC 8785 JSON Canonicalization Scheme is a candidate serialization basis, subject to the contract constraints above. JCS does not itself define application semantics or make absent and null equivalent.

## 6. Durable state machine and linearization

Durable operation states:
- `COMMITTED`: the canonical memory effect and replayable result committed atomically.
- `CLOSED_NO_EFFECT`: a durable tombstone proves that the operation namespace was closed before any effect committed.

`IN_PROGRESS` is permitted only inside an uncommitted transaction. It must never be externally visible as a durable state. Database enforcement must prevent a committed ledger row from remaining in `IN_PROGRESS` (for example, through a deferred constraint trigger or a controlled write procedure with restricted direct DML).

`UNRESOLVED` is an API interpretation, not a durable ledger state. It is returned when the service cannot establish a terminal outcome within the request's bounded wait. It must never be mapped to `NOT_FOUND`, `not_stored`, or success.

### 6.1 Create

One PostgreSQL transaction must:
1. Authenticate and authorize the caller.
2. Validate the canonical request and calculate its fingerprint.
3. Acquire the required security and resource-fence locks in the global lock order.
4. Claim the operation namespace under a unique constraint.
5. Compare the fingerprint if the key already exists.
6. Insert the memory effect into the one authoritative memory store.
7. Persist the terminal ledger state and replayable response.
8. Commit all database-local effects atomically.

The Create linearization point is the transaction COMMIT. Success must not be emitted before the required commit and durability level are established.

Same key + same fingerprint returns the prior committed result. Same key + different fingerprint returns `IDEMPOTENCY_CONFLICT`. A rolled-back transaction leaves no durable partial operation claim or memory effect.

### 6.2 Close / terminalize UNKNOWN

Create and Close use the exact same uniqueness namespace.

- If Create commits first, Close returns `ALREADY_COMMITTED`.
- If Close commits first, it creates `CLOSED_NO_EFFECT`; all late Create requests for that key are rejected.
- If the operations race, the unique constraint and transaction serialization select exactly one terminal winner.
- If the bounded wait expires before the winner can be established, return `UNRESOLVED`; do not infer absence.

A plain status read returning no visible row is not proof that no request is in flight. Only a committed `CLOSED_NO_EFFECT` tombstone, serialized against Create acceptance, authorizes a caller to resolve its local UNKNOWN as having no effect.

### 6.3 Status

Status must distinguish terminal evidence from uncertainty:
- `COMMITTED`: return the stored replay result, subject to current authorization.
- `CLOSED_NO_EFFECT`: return the terminal closure evidence.
- A competing uncommitted transaction or bounded wait: `UNRESOLVED`.
- No visible row: not proof of non-dispatch, non-acceptance, or absence of an in-flight request.

## 7. PostgreSQL transaction and concurrency rules

- Enforce the operation namespace with a database unique constraint.
- Keep the memory effect, ledger terminal state, and replayable response in one transaction.
- At PostgreSQL READ COMMITTED, after `INSERT ... ON CONFLICT DO NOTHING` reports no insert, perform a separate subsequent SELECT so it receives a fresh statement snapshot.
- Under SERIALIZABLE, retry the entire transaction after serialization failure (SQLSTATE `40001`); do not retry only the failed statement.
- Do not depend on PostgreSQL 19-specific `ON CONFLICT DO SELECT` until the deployed PostgreSQL major version is confirmed.
- Bound lock waits and transaction duration. A timeout produces `UNRESOLVED`, not a claim of no effect.
- All participating routes must follow one global lock order:

```text
principal_security_state
  -> resource_fences
  -> operation_ledger
  -> memory
```

The implementation must validate that no code path takes these locks in reverse order.

## 8. Backend-authoritative fencing

A Hub-local lease or monotonically increasing token is insufficient. The protected write resource must authoritatively validate the current fence.

Proposed `resource_fences` record:
- `resource_scope`
- `fence_epoch`
- `owner_id`
- `lease_expires_at`
- `updated_at`

Write protocol:
- A write locks the fence row with a lock compatible with concurrent writes but conflicting with ownership transfer (proposed `SELECT ... FOR SHARE`).
- The write validates owner and epoch inside the same transaction that performs the protected effect.
- Ownership transfer locks the same row for update, increments the epoch, changes owner, and commits.
- If the write obtains its lock first, transfer waits until the write transaction ends.
- If transfer commits first, the old epoch is rejected.
- Lease expiry alone does not prove ownership transfer; the authoritative epoch transition is required.

This database fence protects only writers sharing the same authoritative database. Multiple independent primaries or split-brain deployments require infrastructure-level fencing and a single authoritative ownership/consensus mechanism. Before failover promotion, the old primary must be prevented from accepting writes.

## 9. Authorization and replay

- Authenticate and authorize before returning a replay result.
- Bind the operation to the authenticated `subject_id`; do not trust a caller-supplied identity.
- Maintain `principal_security_state.auth_epoch`.
- Replay reads and validates the current authorization epoch in the same transaction/serialization boundary used for the replay decision.
- Revocation increments the epoch under the same authoritative database boundary.
- If identity-provider revocation is external and cannot be transactionally ordered with Backend operations, the system must state that limitation and must not claim atomic revocation semantics.
- Administrative Close requires explicit permission, records the acting principal, and does not create a separate operation-key namespace.

## 10. One authoritative Memory source and Legacy compatibility

The existing `memory` table remains the sole authoritative memory store unless a separately approved migration explicitly replaces it as the single source of truth. Do not introduce a parallel `memory_entries` store that creates dual authority.

A migration may add canonical fields such as:
- `canonical_id`
- `contract_version`
- `summary`
- `source`
- `metadata`
- `field_presence`

Existing integer `id` values remain available for legacy compatibility. `field_presence` or an equivalent representation must preserve absent-versus-null semantics. Historical rows must not receive fabricated canonical values.

Legacy endpoints remain available through one Compatibility Facade that calls the same canonical services. They must not contain duplicate validation or persistence logic.

**Loss-preservation rule:** No Legacy path may discard or default a value that is representable in the Canonical contract. If a legacy response cannot represent a canonical record losslessly, reject the projection with an explicit error such as `LEGACY_PROJECTION_UNSUPPORTED`; never silently truncate, coerce, or fabricate data.

Legacy clients that do not supply a stable operation key do not receive the CMWP idempotency guarantee. Their limitation must be explicit and observable. The Hub's existing interaction/content hash is not a substitute for a stable operation key.

## 11. Retention and expiry

- A key or tombstone must remain authoritative for the full period during which a delayed request or retry can still arrive.
- Do not physically delete a tombstone while a late request can be accepted under the same namespace.
- If finite retention is required, define an authoritative key-generation/epoch policy that rejects stale keys after expiry; elapsed time alone is not proof that old requests have stopped.
- Retention guarantees are bounded by the declared validity horizon and ingress policy.
- A retry after canonicalizer upgrade must still be evaluated under the original canonicalization version for the key's validity period.

## 12. Durability contract

The API must distinguish:
- `LOCAL_DURABLE`: the local primary's WAL commit record has reached the configured local durability boundary.
- `SYNC_REPLICA_DURABLE`: the commit has reached the configured synchronous standby acknowledgement boundary.
- `FAILOVER_SAFE`: the deployment's promotion policy guarantees that a replica containing every acknowledged commit is selected and the former primary is fenced.

PostgreSQL asynchronous replication is the default unless configured otherwise. `synchronous_commit=on` alone does not prove failover-safe durability. The actual synchronous standby configuration, acknowledgement mode, replication topology, promotion policy, and old-primary fencing must be verified.

The response must not claim a stronger durability level than the deployment has established. If the requested level is unmet, return `DURABILITY_LEVEL_UNMET` or an explicitly uncertain outcome according to whether COMMIT may already have occurred.

## 13. External side effects

A PostgreSQL transaction can make only its own database-local effects atomic. Notifications, webhooks, queues, external APIs, and other independent systems are outside this transaction.

For external effects, use a transactional outbox, durable message identity, idempotent consumer, and destination-side idempotency/fencing where supported. An outbox by itself does not establish exactly-once delivery or effect. Report partial/unknown external outcomes honestly; do not infer success or failure from a local database commit.

## 14. Error contract

The implementation should define stable machine-readable errors, including:
- `IDEMPOTENCY_CONFLICT`
- `STALE_FENCE`
- `OPERATION_CLOSED`
- `ALREADY_COMMITTED`
- `CANONICALIZATION_VERSION_UNSUPPORTED`
- `AUTHORIZATION_REVOKED`
- `OPERATION_OUTCOME_UNKNOWN`
- `SERIALIZATION_RETRYABLE`
- `DURABILITY_LEVEL_UNMET`
- `LEGACY_PROJECTION_UNSUPPORTED`

Error responses must not disclose secrets, internal tokens, or unauthorized replay payloads. Retryability and whether the operation may have committed must be explicit.

## 15. Formal invariants

The following invariants are mandatory model and implementation obligations.

| ID | Invariant | Required property |
|---|---|---|
| INV-01 | Type and namespace safety | Every operation is bound to one valid, fully scoped identity tuple. |
| INV-02 | At-most-one effect | At most one canonical memory effect exists per scoped idempotency key. |
| INV-03 | Ledger/effect atomicity | A committed memory effect and its terminal ledger/replay record exist together or neither exists. |
| INV-04 | No committed IN_PROGRESS | No durable ledger record remains in a non-terminal state. |
| INV-05 | Create/Close exclusivity | A key cannot be both COMMITTED and CLOSED_NO_EFFECT. |
| INV-06 | Immutable fingerprint | A key's canonicalization version and request fingerprint cannot change. |
| INV-07 | Authorized replay | A replay is returned only after current authorization is validated. |
| INV-08 | Stale-owner exclusion | A write with a superseded fence epoch cannot commit. |
| INV-09 | Single Memory authority | Canonical and Legacy writes converge on one authoritative memory store. |
| INV-10 | Lossless Legacy projection | A non-representable canonical value is rejected, never silently lost or defaulted. |
| INV-11 | Tombstone validity | A closure tombstone remains authoritative for the entire key-validity horizon. |
| INV-12 | No false success | No success response is emitted before the required transaction commit and durability boundary. |
| INV-13 | Honest durability acknowledgement | The ACK's declared durability level is no stronger than verified deployment guarantees. |
| INV-14 | External-effect honesty | Database commit is never represented as proof that an independent external effect succeeded exactly once. |

## 16. Hostile test matrix

Each test must be reproducible, deterministic where possible, and preserve logs, transaction traces, SQLSTATEs, timing/barrier configuration, database version/configuration, and the exact source revision.

| ID | Attack / setup | Required outcome |
|---|---|---|
| CE-15 | Query Status while Create is uncommitted and another transaction holds the key. | Return UNRESOLVED or wait within a bounded policy; never NOT_FOUND/not_stored. |
| CE-16 | Race Create and Close for the same namespace/key. | Exactly one terminal outcome; loser observes the winner's terminal state. |
| CE-17 | Let a lease expire without transferring the authoritative fence epoch. | No new owner is inferred from time alone; stale writes remain governed by the current epoch. |
| CE-18 | Race authorization revocation against replay. | A deterministic serialization order; no replay after a revocation that wins the authoritative order. |
| CE-19 | Write the same logical record through Legacy and Canonical routes concurrently. | One authoritative store and no duplicate logical effect under the declared identity contract. |
| CE-20 | Attempt to delete a closure tombstone, then deliver a delayed Create. | Deletion is prohibited during key validity, or stale ingress is rejected by an authoritative epoch policy. |
| CE-21 | Force a serialization failure during a multi-step write. | Retry the entire transaction; no partial ledger or memory effect. |
| CE-22 | Fail over after an acknowledged commit. | Preserve the acknowledged effect to the exact durability level declared by the response. |
| CE-23 | Upgrade canonicalization while a key remains valid, then retry the original request. | Evaluate using the key's original canonicalization version; same request replays. |
| CE-24 | Crash after commit but before the response reaches the client. | Retry with the same key returns the prior result without a second effect. |
| CE-25 | Have an authorized administrator Close an operation created by a different actor. | Close targets the original operation namespace; actor identity and authorization are audited separately. |
| CE-26 | Use identical key strings in two distinct client namespaces. | No cross-namespace collision or replay leakage. |
| CE-27 | Retry a key after its nominal expiry while a delayed request may still arrive. | Reject stale ingress through an authoritative expiry/epoch policy; never rely only on elapsed time. |
| CE-28 | Read a canonical record through a Legacy projection that cannot represent one or more fields. | Return an explicit projection error; preserve the canonical record unchanged. |

## 17. Acceptance gates

No implementation is accepted until all applicable gates are satisfied:

1. Database schema and unique constraints enforce the exact operation namespace.
2. Real PostgreSQL multi-session tests prove Create/Create and Create/Close races.
3. Memory effect, ledger terminal state, and replay response are transactionally atomic.
4. Status never confuses an uncommitted/in-flight operation with proven absence.
5. Backend-authoritative fencing is validated under concurrent writes and owner transfer.
6. Authorization and replay ordering are tested against the actual identity architecture.
7. Canonicalizer upgrade and key-retention behavior are tested across supported versions.
8. Crash-before-commit and crash-after-commit-before-response cases are exercised.
9. Failover tests verify the declared durability level against actual replication and promotion configuration.
10. Legacy routes use the same canonical service and reject lossy projections.
11. OpenAPI documents status, Close, error, replay, and durability semantics.
12. Formal model checking is run with an actual supported checker (e.g. TLC), with model configuration and counterexamples retained.
13. Deterministic PostgreSQL stress/fault harness results are reproducible from a pinned revision.
14. Independent adversarial review verifies evidence, counter-evidence, assumptions, and falsification conditions.

A green unit test suite alone does not satisfy these gates.

## 18. Formal verification plan

The formal model must include at least:
- Two clients, two logical requests, and two payloads.
- Concurrent Create/Create and Create/Close.
- Crash, restart, response loss, and failover.
- Fence epoch changes and stale-owner writes.
- Authorization epoch changes and replay.
- Canonicalization-version changes and key expiry.
- Tombstone retention and delayed ingress.
- Explicit safety invariants INV-01 through INV-14.
- Liveness properties stated with their fairness, availability, and infrastructure assumptions.

The model must expose reproducible counterexamples when a required mechanism is removed. A custom Python state explorer is useful exploratory evidence but is not TLC and is not a substitute for formal TLA+ model checking. No TLC execution is claimed by this design document.

## 19. Evidence and verdict discipline

Every material claim must be labeled as one of:
- **REJECTED**
- **DISPUTED**
- **PROVISIONALLY SUPPORTED**
- **UNKNOWN**

Unknown is neither pass nor fail. Evidence records must distinguish direct source evidence, derived inference, model assumptions, empirical observations, and independent verification. Record counter-evidence, rival hypotheses, falsification conditions, and the test that would distinguish them.

The Master Brain Proof Audit integration may organize and trace evidence, but an output of `evidence_supplied_not_independently_verified` is not an independent verification verdict.

## 20. Open decisions before implementation

These decisions must be resolved against the actual target deployment and contract before implementation:
1. Exact PostgreSQL major version and supported SQL/locking features.
2. Actual replication topology, synchronous acknowledgement mode, and promotion/fencing policy.
3. Identity provider integration and whether revocation can be ordered transactionally at the Backend.
4. Exact tenant, principal, and client namespace derivation and lifecycle.
5. Canonical schema, numeric domain, field-presence representation, and unknown-field policy.
6. Key validity horizon and authoritative stale-key rejection mechanism.
7. Whether administrative Close is exposed as a separate permissioned API route and its audit requirements.
8. Required durability level for each operation class.
9. Legacy client inventory and migration/retirement criteria.
10. External side-effect inventory and destination idempotency capabilities.
